미니골프 미니게임 리팩토링 및 완성

문제 외주에서 미완성 상태로 넘어온 미니게임이 Child Actor로 고정 배치된 구조였고 설계 문서가 없음판단 코드와 실제 플레이로 구조를 파악하고 DataTable 기반 스폰으로 전환결과 18개 스테이지 재구현과 데이터 파이프라인까지 핵심 구현을 약 2주에 1인으로 마침

상호작용 시스템 범용화 리팩토링

문제 의자 이름 문자열로 식별해 서버가 대상을 검증할 수 없었음판단 등록 방식 3가지 중 범용 서브시스템이 ObjectId로 조회하는 B안 선택결과 의자·상점 NPC 패킷을 범용 상호작용 패킷 하나로 통합

의자 이름 문자열로 식별하고 의자 Actor 하나가 모든 처리를 맡던 라이브 구조를, Actor 단위 정수 ObjectId 기반 범용 구조로 설계·전환했습니다.

  • 분석 · 설계 · C++ 리팩토링 · 에디터 도구 · 서버 협의

문제

라이브 구조는 의자 Actor 하나가 클릭·패킷·위젯·좌석을 모두 처리하고, 서버에는 의자 이름 문자열을 보냈습니다. 서버가 대상을 검증할 기준이 없었고, 상호작용 타입이 늘 때마다 전용 서브시스템이 하나씩 생기는 구조였습니다.

판단

오브젝트 등록 방식을 3가지로 비교했습니다. A안(각 Action이 서버 서브시스템에 직접 등록)은 서버 서브시스템의 책임이 과중해지고, C안(Multicast 델리게이트)은 이벤트마다 전체를 순회합니다. 그래서 B안(범용 서브시스템이 ObjectId로 조회)을 택했습니다.

구현

  • 상호작용 오브젝트 DataTable 행을 설계했습니다(ObjectId · LevelType · InteractionType · ObjectLocation · 레벨 인스턴스 여부 · WorldType · SeatCount). 이 테이블을 CSV로 추출해 클라이언트와 서버가 같은 데이터로 검증하게 했습니다.
  • InteractionSubsystem은 TMap<uint32, TWeakObjectPtr<UInteractionComponent>>로 ObjectId를 매핑하고, 레벨 로드 시 TActorIterator로 자동 스캔·등록합니다.
  • 좌석 단위 점유와 가장 가까운 빈 좌석 배정을 구현하고, 상점 NPC까지 같은 구조로 확장했습니다.
  • 의자·상점 NPC 전용 패킷을 ObjectId · 상호작용 타입 · 동작 타입 · 동작 데이터로 구성된 범용 상호작용 패킷 하나로 통합했습니다.
  • 레벨과 레벨 인스턴스의 상호작용 Actor를 스캔해 ObjectId를 순차 부여하고 DataTable에 등록(같은 행은 갱신)하는 에디터 도구를 만들었습니다. C++ 지원 함수 10종과 EUW로 구성했고, 기존 의자 ID 전용 도구 4종은 정리했습니다.
  • 패킷 변경 사항과 서버 계획서, 흐름 비교 문서를 작성해 서버 개발자와 에러 코드·동작 타입·브로드캐스트 범위를 협의했습니다.

상점 시스템 게임서버 전환 및 프레임드랍 최적화

문제 상점만 REST로 남았고, 전환 후 첫 오픈에 프레임 스파이크(최종 수정 전 코드 재측정 248~303ms)판단 가변 길이 단일 패킷으로 사양 확정, Insights로 Definition 동기 로딩을 병목으로 확정결과 2단계 비동기 프리로딩과 소프트 레퍼런스로 첫 오픈 프레임 최대 44.3ms (에디터 PIE)

상점 통신을 REST에서 게임서버 TCP 패킷으로 전환하고, 전환 후 발견한 첫 오픈 프레임 스파이크(최종 수정 전 코드 재측정 248~303ms)를 Unreal Insights로 추적해 비동기 프리로딩으로 해소했습니다.

  • 패킷 도착 순서가 바뀌어도 열리도록 상점 오픈 조건을 양쪽에서 검사하게 했습니다.
  • 상점 UI가 뜨지 않던 문제 3건을 순서대로 해결했습니다.

    3. BlueprintImplementableEvent 시그니처 변경으로 무효화된 Blueprint 이벤트 → C++ 경로로 이관
  • 구매 성공 델리게이트를 통화 갱신에서 분리해, 퀘스트 보상 등 상점 밖의 잔액 변동과 섞이지 않게 했습니다.

Unreal Insights 기반 프레임드랍 최적화

문제

상점을 처음 열 때 프레임 스파이크가 발생했습니다. 최초 발견 당시 작업 문서의 Insights 기록은 프레임 541ms 중 동기 에셋 로딩 540ms였습니다(원본 트레이스 미보존). 최종 수정(3차 프리로딩과 소프트 레퍼런스)을 되돌린 코드로 다시 측정하면 첫 오픈 프레임 248~303ms 중 동기 로딩이 64~66회 실행되며 92~93%를 차지했습니다.

원인 (2계층)

① 아이템 정의 조회가 메모리에 없는 Definition Blueprint를 게임 스레드에서 동기 로딩했습니다. ② 탈것 Definition이 스폰 Actor 클래스를 TSubclassOf<AActor> 하드 레퍼런스로 들고 있어 탈것 Blueprint·메시·머티리얼까지 연쇄 로딩됐습니다.

  1. 1차 썸네일만 비동기 프리로딩 → 효과 미미. 병목이 텍스처가 아니라 Definition임을 확인
  2. 2차 프리로딩 완료를 기다린 뒤 UI 오픈 → 부분 개선. Insights로 진짜 병목(Definition 동기 로딩) 확정
  3. 3차 RequestAsyncLoad 기반 Definition → 썸네일 2단계 비동기 프리로딩 + 콜백 체인

  • Render Target 용도별 최적화 — 알파 마스크용 캡처는 RGBA8, 색상 캡처는 RGBA16f로 바꾸고 해상도를 2048 → 1024로 낮췄습니다. 색상 캡처까지 RGBA8로 바꾸면 모바일 Vulkan에서 검게 출력되는 문제를 실기기 검증에서 발견해, 색상 캡처만 RGBA16f로 유지했습니다. 이 단계에서 프레임은 약 20ms가 됐습니다.
  • 성별 선택 상태에 따른 캡처 제어 — 성별을 고르면 화면에 보이지 않는 성별의 캡처를 멈추고, 성별 선택 화면으로 돌아오면 다시 켭니다. 로직은 C++ 위젯 함수로 구현해 Blueprint 성별 선택 흐름에 연결했습니다.
  • 카메라 이동으로 멈춘 캡처가 다시 실행되지 않도록 매 프레임 캡처와 이동 기반 캡처를 함께 제어했습니다. 아바타가 idle 애니메이션을 재생하므로 보이는 캡처는 매 프레임 갱신을 유지했습니다.

문제

순찰 캐릭터의 이동을 다른 유저에게 어떻게 전달할지 정해야 했습니다. 순찰 계정임을 로그인 직후 통지하는 초안도 성립하지 않았습니다. 계정 식별자가 로그인 요청이 아니라 그 뒤의 입장 요청에 처음 실리기 때문입니다.

판단

순찰 클라이언트가 경로를 걷고 일반 캐릭터와 같은 주기로 위치를 보내는 기존 이동 패킷 재사용을 골랐습니다. 순찰 여부·담당 구역·캐릭터 종류는 입장 응답에 싣는 것으로 서버 담당자와 맞췄습니다.

서버와의 계약 조율

  • 입장 응답 기준 분기 — 입장 응답으로 순찰 계정을 판별하면 월드 선택 화면에서 지역을 고르지 않고 담당 구역으로 자동 이동합니다. 순찰 계정은 서버와 합의한 허용 패킷만 보내고 랭킹·퀘스트·튜토리얼 요청은 생략합니다.
  • 전용 빌드를 두지 않기로 한 뒤의 대응 — 일반 빌드는 입장 응답 전까지 자신이 순찰 계정인지 모릅니다. 그래서 순찰 계정 닉네임 채우기(비어 있으면 캐릭터 생성 화면으로 빠짐)와 중복 접속 전용 에러 코드를 서버 쪽에 추가로 요청했습니다.
  • 배포 순서 의존성 — 일반 유저 클라이언트도 외형 정보가 빈 순찰 캐릭터 생성 패킷을 받게 되므로, 새 프로토콜로 내는 빌드에는 순찰 캐릭터 표시 처리가 함께 들어가야 한다는 점을 찾아 서버 담당자와 배포 순서를 조율했습니다.
  • 서버 없이 먼저 개발 — 에디터 전용 디버그 스위치와 테스트 레벨을 만들어 순찰 코어를 먼저 구현하고 자동 테스트를 함께 넣은 뒤, 서버 계약이 확정되고 나서 연동을 붙였습니다.

순찰 전용 캐릭터 구성

  • 아트팀이 만든 순찰 NPC에 순찰 계정이 빙의하는 구조를 먼저 검토했지만, 그 NPC는 빙의할 수 없는 액터였고 액터는 제자리에 둔 채 메시만 움직이는 방식이라 카메라와 이동 패킷이 따라갈 위치가 없었습니다. 마스코트 2종은 골격이 서로 다르고 걷기 애니메이션 하나뿐이라 기존 플레이어 캐릭터 구조에도 맞지 않았습니다.
  • 순찰 전용 캐릭터·컨트롤러·HUD를 새로 만들고 아트 에셋은 메시와 걷기 애니메이션만 가져왔습니다. 교체 지점을 GameMode 한 곳으로 모아 순찰 세션일 때만 세 클래스를 바꿔 끼우고, 기존 플레이어 클래스는 건드리지 않아 일반 유저 흐름에 영향이 없게 했습니다.
  • 경로 추종은 시작·중지·재개·반복을 지원하고, 전용 HUD(초상화·이름·구역·시작/중지·로그아웃)를 디자인 시안대로 만들었습니다.
  • 일반 유저 쪽에서는 순찰 마스코트를 플레이어 목록과 따로 관리해 프로필 보기·음성통화·이모티콘 대상에서 빠지게 했습니다.

이동 방식 전환 — 물리 걷기에서 경로 직접 추종으로

  • 처음에는 경로 위 1m 앞 지점을 목표로 걷게 하고 실제 이동은 캐릭터 이동 컴포넌트에 맡겼습니다. 경로를 벗어나면 복구하고, 반복되면 팝업을 띄우게 했습니다.
  • 경로를 만들 때 쓴 내비게이션 메시가 낮은 울타리를 장애물로 보지 않아 마스코트가 울타리에 막혀 멈췄습니다. 캡슐 크기로 경로 전체를 25cm 간격으로 다시 검사해 경로를 옮겼지만, 장시간 무인 실행에서는 언젠가 어딘가에 막힐 위험이 남았습니다.
  • 그래서 바닥만 밟고 나머지는 모두 통과하도록 바꿨습니다. 충돌을 무시하고 이동 컴포넌트를 끈 뒤, 매 프레임 경로 위 거리를 걷기 속도만큼 늘려 직접 옮깁니다. 높이는 발밑 위 45cm ~ 아래 100cm 범위에서 바닥을 찾아 맞춰, 계단과 경사는 따라가고 머리 위 구조물은 무시합니다. 이탈 복구 로직과 이탈 팝업은 필요 없어져 삭제했습니다. 에디터 플레이(8배속) 한 바퀴 기준 경로 이탈 최대값은 33~34cm에서 7cm로 줄었고 이동 속도는 일정했습니다.
  • 충돌을 완전히 끄면 엔진이 주는 캐릭터 키 값이 0이 되어 카메라 높이 계산이 깨졌습니다. 충돌은 켜 둔 채 모든 채널을 무시하게 했습니다.
  • 물리 이동이 없으면 속도가 0이라 이동 패킷과 걷기 애니메이션이 멈췄습니다. 속도 값을 경로 방향 × 걷기 속도로 직접 채웠습니다.
  • 중력이 없어 시작 지점 높이에 떠 있던 문제는 빙의 시점에 바닥에 한 번 세우도록 해결했습니다.

카메라

  • 시점 드래그가 동작하지 않던 버그는 회전 입력을 엔진의 프레임 처리 뒤에 넣어 매 프레임 버려지던 것이 원인이었습니다. 이전 확인은 회전 값을 직접 설정하는 방식이라 이 문제를 잡지 못했고, 입력을 넣는 순서를 엔진 처리 앞으로 옮겨 해결했습니다.
  • 장애물 회피는 새로 만들지 않고 프로젝트에 있던 3인칭 카메라 로직을 재사용했습니다. 구 형태 스윕 5개로 감지해 막히면 즉시 당기고 0.15초에 걸쳐 복귀합니다(에디터 실측 카메라 거리 403cm → 191cm → 403cm).

경로 배치와 협업 충돌

  • 두 구역에 순찰 경로와 전용 시작 지점을 배치했습니다. 기획 동선 중 실제 레벨에서 들어갈 수 없는 곳(담으로 막힌 구역, 건널 수 없는 다리, 높은 단)은 바깥으로 도는 경로로 바꾸고 기획·아트 확인 사항으로 남겼습니다.
  • 아트 브랜치가 같은 레벨을 따로 수정해 충돌했을 때는 아트 쪽 버전을 채택하고, 미리 뽑아 둔 순찰 경로 210개 지점과 시작 지점을 오차 없이 다시 배치했습니다. 같은 일이 생기면 다시 쓸 수 있게 추출본을 남겼습니다.

경로 이탈과 카메라 수치는 에디터 플레이 실측이며, 경로 이탈은 8배속으로 측정했습니다. 빌드·자동 테스트·에디터 플레이에 더해, Windows 빌드에서 실제 서버의 순찰 계정으로 접속해 마스코트 진입과 순찰 시작·중지·재개를 확인했고, 다른 유저 화면에 같은 마스코트가 보이는 것도 확인했습니다.

신규 백엔드 이관 — 로그인·버전/점검·우편·이벤트·친구

문제 계정 식별자가 UUID로 바뀌는 등 신규 백엔드와 기존 계약이 맞지 않음판단 UUID를 숫자 ID로 임의 매핑하지 않고 경계를 명시결과 로그인·버전/점검·우편·이벤트 API 이관과 실서버 검증, 친구 API 2차 이관

백엔드 교체(이관 당시 구 136개 → 신 81개 엔드포인트)에 맞춰 로그인·가입·버전/점검·우편·이벤트 API를 신규 계약으로 옮기고, 맞지 않는 계약은 억지로 끼우지 않고 경계를 명시했습니다.

  • 2026.08 ~ 10
  • REST 계약 이관
  • 계약 테스트
  • 실서버 검증

문제

신규 백엔드의 계정 식별자는 UUID 문자열인데 기존 게임 입장은 숫자 계정 ID를 썼습니다. 사용자 재화 조회 API는 퇴역했고, 우편 ID는 64비트 정수로 바뀌었습니다.

판단

UUID를 숫자 ID로 임의 매핑하지 않았습니다. 표준 36자 형식만 허용하고 검증에 실패하면 버퍼를 전부 초기화하며, 검증을 통과해야만 토큰을 저장합니다. 게임 입장 패킷 변경은 서버 생성물이 확정본이라 서버팀에 제안서로 전달했습니다.

  • 이관 전에 기존 코드가 쓰는 웹 API 43개의 실사용 여부를 먼저 감사했습니다.
  • ID/비밀번호 로그인·가입 위젯, 버전 체크·점검 상태, 64비트 우편 ID, 이벤트·뉴스·알림 API를 이관하고 계약 테스트를 작성했습니다.
  • 실서버에서 회원가입부터 로그인까지 전 과정과 우편·이벤트 API 동작을 검증했습니다.
  • 10월에는 친구(목록·요청), 우편 보상 목록, 알림 읽음, 채널(게임서버 주소) API를 2차로 이관하고, 1:1 음성통화 토큰 발급 흐름(통화 만료·늦은 응답·중복 종료 처리)을 구현했습니다.
  • 전환 중 실패 원인도 규명했습니다. 요청 객체가 URL을 /로 초기화해 경로의 슬래시가 겹치던 결함을 찾았고, 신규 서버가 없는 경로에도 404 대신 401을 준다는 특성을 정리해 인증 문제로 오인하지 않게 했습니다.

엔진 내장 웹뷰가 최신 웹 로그인 페이지를 띄우지 못하고 카메라·마이크도 동작하지 않아, 웹을 OS 브라우저에서 열고 결과를 커스텀 스킴 딥링크로 받는 구조로 바꿨습니다.

  • 2026.06 ~ 10
  • Android · iOS · Windows
  • Chrome Custom Tabs
  • SFSafariViewController
  • 커스텀 스킴 딥링크

문제

엔진 내장 웹뷰(구버전 Chromium)가 웹팀의 최신 JS 번들을 파싱하지 못해 로그인 페이지가 흰 화면으로 떴습니다. 같은 웹뷰에서 카메라·마이크도 동작하지 않았습니다.

판단

엔진을 패치하는 대신 시스템 브라우저에서 웹을 열고 결과를 딥링크로 받기로 했습니다. 카메라·마이크는 엔진 웹뷰 소스까지 추적해, 웹의 미디어 권한 요청을 처리하지 않아 기본 거부된다는 원인을 확인하고 같은 OS 브라우저 방식으로 해결했습니다.

  • Android(intent-filter)·iOS(URL scheme)·Windows(프로토콜 등록과 실행 중인 앱으로 넘겨주는 런처) 딥링크 수신부를 만들었습니다.
  • 로그인 시도 단위 대기 플래그로 요청하지 않은 딥링크는 거부하고, 시도 일련번호로 이전 시도의 늦은 응답을 무시했습니다. 프로필 조회로 계정 식별자를 다시 확인한 뒤 로그인을 마무리합니다.
  • 게임서버에 연결되지 않은 상태면 로그인을 시작하지 않게 했고, Windows 프로토콜 실행이 URL 형태를 바꿔 딥링크가 버려지던 문제를 고쳤습니다. PIE에서 딥링크 콜백을 재현하는 콘솔 명령도 만들었습니다.
  • 이 흐름을 정식 로그인으로 확정해 전환하고, 토큰 만료 시 강제 로그아웃과 웹 로그아웃 딥링크 처리를 추가했습니다.
  • Android·iOS·Windows에서 웹 로그인 후 게임서버 로그인까지 확인했고, 웹 미디어는 Android 실기기에서 카메라 동작을 확인했습니다.

플랫폼별 조명 분리 — 모바일은 구운 조명, Windows는 실시간 조명

문제 한 레벨에서 모바일은 구운 조명을, Windows는 실시간 조명(Lumen)을 써야 함판단 레벨을 플랫폼별로 2개 운용하지 않고 조명만 서브레벨 2개로 분리결과 Windows 콘텐츠 청크 약 129.6MB 감소, 모바일 청크 크기 변화 없음

한 레벨에서 모바일은 기존 구운 조명을, Windows는 실시간 조명(Lumen)을 쓰도록 조명을 플랫폼별 서브레벨 2개로 나눴습니다.

  • 2026.11
  • 서브레벨
  • Lumen
  • 패키징 규칙
  • 실행 중인 렌더러에 맞는 조명 서브레벨을 불러오는 서브시스템을 만들었습니다.
  • Windows 패키지에서는 모바일용 구운 조명 데이터를 빼도록 패키징 규칙을 추가했습니다.
  • 레벨을 플랫폼별로 2개 운용하는 안은 배치 변경을 두 번 해야 해서, 색감만 옮기는 안과 함께 버렸습니다.
  • 조명 굽기는 약 1시간 40분, 조명 맵 6,444개였습니다. 에디터의 같은 시점에서 분리 전과 분리 후 모바일 화면의 평균 픽셀 차이는 약 2/255였습니다.

에디터 비교, 3플랫폼 풀빌드, Windows 청크 크기 비교까지 확인해 릴리스에 반영했습니다. 모바일 실기기의 화면·프레임 확인은 아직 하지 않았습니다. 레벨과 라이팅 원본은 아트 담당 작업입니다.

기타

  • 스마트폴 현황(Mock) — 외부 API가 아직 없어 클라이언트 Mock 데이터로 시설 현황 UI를 먼저 완성하고, 실연동 때 데이터 소스만 바꾸도록 분리했습니다.
  • 신규 회원 튜토리얼 — 입장 패킷의 튜토리얼 상태로 신규 회원을 판별해 첫 진입 튜토리얼(표지 → 12쪽 이미지 가이드 → 완료 팝업)을 월드맵에서 한 번 표시합니다. 이미지는 REST 목록으로 받아 기존 안내 팝업을 재사용했고, 완료 패킷은 실패·무응답에 대비해 최초 전송을 포함해 최대 3회까지 보내도록 구현했습니다.
  • 튜토리얼 이미지 메모리 — 튜토리얼에서 이전/다음을 반복하면 GPU 메모리 부족으로 앱이 종료됐습니다. 서버 이미지가 약 4천만 화소라 텍스처 1장이 CPU와 GPU에 각각 약 154MB(화소 수 기준 계산값)를 썼고, 화면에서 벗어난 텍스처가 다음 가비지 컬렉션까지 남아 쌓였습니다. 안내 팝업 이미지는 긴 변 2048px 이하로 줄여 텍스처를 만들고, 현재 쪽 앞뒤 1쪽 밖의 텍스처는 바로 해제하며, 받는 도중 범위를 벗어난 쪽은 디코딩하지 않게 했습니다. 16-bit PNG 버퍼 넘침, 흑백 이미지 깨짐, 모바일 JPEG의 빨강·파랑 뒤바뀜도 함께 고쳤습니다. 수정 후 실기기 재현 확인은 아직 하지 않았습니다.
  • 이미지·영상 빌보드 — 광장 빌보드 16개에 관리자 페이지에서 지정한 이미지를 표시하고, 해제되면 원래 모습으로 되돌립니다. 슬롯 상태를 서브시스템이 보관해 패킷 수신과 빌보드 생성 순서에 상관없이 같은 결과가 나오게 했고, 슬롯 키 규약은 문서로 서버팀과 합의했습니다. 영상 빌보드는 초기 정리 때 지운 영상 플레이어 위젯 코드를 되살려 새 백엔드의 영상 API로 옮겼습니다. 이미지 빌보드는 Windows 빌드에서 서버가 보낸 이미지 16개가 표시되는 것을 확인했고, 영상 빌보드의 실서버 연동 확인은 아직입니다.
  • 즐겨찾기 TCP 연동 — 관광지 즐겨찾기 조회·등록·해제를 게임 서버 TCP로 연동하고 회귀 테스트를 추가했습니다(실서버 검증).
  • FCM 푸시 — Android 푸시 수신 플러그인과, 개발 메뉴에서 자기 기기로 보내 보는 테스트 도구를 만들었습니다. 테스트 토큰은 게임 인증 토큰과 분리했습니다. iOS는 수신 구현과 빌드 설정(푸시·서명)까지 진행했습니다.
  • Android 요구사항 대응 — 인앱결제 제거에 맞춰 Android 결제 SDK 의존성을 제외하고 target SDK 36 요구사항에 대응했습니다.
  • 아바타·아이템 데이터 이관 — 신규 아이템 체계로 DataTable을 옮기고 외형 성별 규약을 정리했습니다(구버전 세이브 호환 포함). 규약 변경 뒤 Blueprint 2곳이 이전 규약으로 값을 만들어 여자 선택 시 이전 성별이 서버로 전송되던 결함은 공용 변환 함수로 고치고 성별 검증 테스트를 추가했습니다. 미리보기 의상 텍스처 흐림을 mip 스트리밍 문제로 규명해, 전역 설정 대신 미리보기 메시에만 적용하고 화면을 나가면 원복했습니다.
